## The connected journey

1. Owner creates the company and invites a teacher.
2. Teacher signs in and accepts the email-bound invitation.
3. Owner creates a course/cohort, assigns that teacher and invites students into it.
4. Teacher publishes a focused lesson and reviews the questions, answer keys, explanations and references before approving a checkpoint.
5. Student opens the daily plan, completes the lesson check-in and submits the checkpoint.
6. Server grades the stored answer choices. Reloads/retries return the saved result; changing browser-supplied scores cannot alter it.
7. Teacher opens concrete evidence, including confident-but-incorrect responses, and assigns a private next step.
8. Student responds; the task awaits review. Teacher resolves it with feedback or returns it for another response.
9. A student can flag a checkpoint answer. The assigned teacher can publish a correction, retire the old checkpoint and publish a revised copy. Historical scores are not silently rewritten.
10. The owner can export the roster, remove access, and review the company's administrative audit trail.

## Security and data behavior

- Every class access checks active company membership and active section/enrollment, not merely a client role or guessed ID. Removal also blocks older assignment, message, material and dashboard paths.
- Teachers cannot read unfinished submission draft content. Students do not receive classmates' individual grade/ranking details.
- Company invitations store token hashes, expire in seven days, bind to the invited email, reserve seats, and reject replay. Imports validate the entire batch before making changes. A company switch clears pending recipient and cohort forms.
- Company mutations use row locks where concurrency affects seats and invitation acceptance. SQLite is for this local demo; PostgreSQL concurrency and deployment behavior still require staging verification.
- Submitted checkpoint results snapshot the questions, keys, explanations and confidence. Published keys are immutable; revised content is a new checkpoint.
- Submission/grade history starts with this release. Old attempts that were never stored cannot be reconstructed.
- CSV exports escape formula-like text. Draft recovery is scoped by account and cohort/resource.
- Expired explicitly provisioned company licences permit reads/exports but block new classroom writes. Legacy organisations without a licence row remain operator-managed until provisioned. Company seats never grant personal AI subscription entitlements.
- Auth/classroom startup no longer eagerly requires an AI provider; the existing AI client initializes when used.

## Migration and rollout

New Alembic revision: `b2b20260911a`, parent `a9f1e8c2b603`. It creates nine tables for company licences/invitations/audit, lessons/completions, checkpoints/attempts, interventions and submission revisions. The migration is frozen and independently tested both up and down with existing user data retained.

For deployment:

1. Back up the database and confirm the previous trust migration is applied.
2. Apply `alembic upgrade head` from the backend environment.
3. Release backend and web together, using the deployment's actual API origin. Do not deploy the demo build that points to localhost.
4. Provision existing organisations' owner memberships and licences deliberately. New companies bootstrap their creator as owner through `/company`.
5. Use the operator tool below for an agreed contract. It defaults to dry-run and does not charge a card:

```sh
python scripts/company_license.py --organization-id COMPANY_ID --seats 50 --plan cohort --expires YYYY-MM-DD
```

Inspect the output, then add `--apply` to save an agreed licence. Seat limits cannot be set below active people plus reserved invitations.

6. Smoke-test two companies on staging, including inactive teacher/student access, invitations, private files, grade history, licence expiry, checkpoint retirement and correction publication.
7. Run the normal application's authentication, storage and notification configuration checks before giving production credentials to customers.

## Explicit boundaries

This is an implemented B2B classroom and cohort-pilot workflow, not a claim of universal enterprise readiness. Company payments are operator/invoice managed; automated company checkout and outgoing invitation email are not connected. SSO/SCIM, LMS grade passback, co-teacher permission matrices, formal compliance certification, native-mobile B2B screens and production load/security validation remain separate work. Existing personal study tools still belong to the normal Cerbyl backend. A role-specific portal and passing tests do not establish learning effectiveness or commercial demand.
